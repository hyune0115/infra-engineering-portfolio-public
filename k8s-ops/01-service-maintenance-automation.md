# 정전/유지보수 대응 서비스 중지·재기동 자동화

## 1. 배경

### 가. 고객 요구사항

1) 계약상 정전 대비 및 고객사 자체 운영을 위한 서비스 기동/중지 매뉴얼 제공이 요구됨
2) 특정 1개 현장이 아니라, 해당 요구사항을 갖는 다수 고객사에 공통 적용 가능한 절차가 필요했음

### 나. 기존 방식의 한계

1) 기존에는 kubelet 등 systemd 데몬만 중지시켰을 뿐, 그 위에서 동작하는 애플리케이션 프로세스를
   정상적으로 먼저 종료시키는 절차 자체가 없었음
2) 컨테이너 런타임이 끊긴 상태에서 애플리케이션이 비정상 종료되는 구조였고, 종료 순서가
   표준화되어 있지 않아 담당자별로 절차가 달랐음
3) 재기동 시에도 각 컴포넌트가 원래 몇 개의 replica로 운영 중이었는지 별도로 기록해두지 않아,
   수동 복원 과정에서 실수 여지가 있었음

## 2. 기대효과

### 가. 안전한 정지/기동 순서 표준화

1) Application → DB/메시징 → systemd(Infra) 순으로 정지, 재기동은 역순으로 진행되도록 순서를
   코드에 내재화
2) 각 단계 완료 여부를 폴링으로 확인한 뒤 다음 단계로 진행해, 순서 누락이나 조기 진행으로 인한
   오류 가능성을 제거

### 나. 상태 복원 정확성

1) 정지 전 Deployment/StatefulSet의 현재 replica 수를 자동 백업하고, 재기동 시 동일한 값으로
   복원해 수동 기록·복원 과정의 실수를 방지

### 다. 장애 자가진단

1) kubelet이 정상 기동되지 않는 경우를 대비해 커널 파라미터/모듈, swap, SELinux 상태를 자동
   수집·저장하여 현장 원인 파악 시간을 단축

### 라. AS-IS / TO-BE 비교

| 항목 | AS-IS | TO-BE |
|---|---|---|
| 정지 대상 | systemd 데몬만 중지 | Application → DB/메시징 → systemd 순으로 전 계층 정지 |
| 정지/기동 순서 | 담당자별 수동 판단 | 스크립트에 순서·의존성 내재화, 단계별 완료 폴링 후 진행 |
| Replica 복원 기준 | 별도 기록 없음 (수동 추정) | 정지 전 자동 백업, 재기동 시 동일 값으로 자동 복원 |
| kubelet 비정상 기동 대응 | 수동으로 원인 확인 | 커널 파라미터/모듈/swap/SELinux 상태 자동 수집·저장 |
| 적용 범위 | 현장별 개별 대응 | 다수 고객사에 공통 적용 가능한 표준 절차 |

## 3. 구성도 (정지·기동 순서)

### 가. 정지 (Application → Infra)

```
STEP 1  Deployment/StatefulSet 현재 replica 수 백업
  │
  ▼
STEP 2  Application 계층(Deployment) replica 0으로 축소 → Pod 종료 폴링 대기
  │
  ▼
STEP 3  DB/메시징 계층(StatefulSet) replica 0으로 축소 → Pod 종료 폴링 대기
  │
  ▼
STEP 4  systemd 계층 정지 (일반 노드: kubelet → crio / DB 서버: mariadb → elasticsearch)
  │
  ▼
정지 완료
```

### 나. 기동 (Infra → Application, 역순)

```
STEP 1  systemd 계층 기동 (crio → kubelet / DB 서버: mariadb → elasticsearch) → 상태 확인
  │
  ├─ kubelet 비정상 기동 시 → 커널 파라미터/모듈, swap, SELinux 상태 자동 수집·저장
  │
  ▼
STEP 2  Control Plane(API/Scheduler/Controller-manager) 상태 확인 후 다음 단계 진행
  │
  ▼
STEP 3  DB/메시징 계층(StatefulSet) 백업된 replica 수로 복원 → 준비 완료 폴링 대기
  │
  ▼
STEP 4  Application 계층(Deployment) 백업된 replica 수로 복원 → 준비 완료 폴링 대기
  │
  ▼
기동 완료
```

## 4. 성과

1) 고객사가 정전·점검 상황에서 자체적으로 안전한 순서에 따라 서비스를 내리고 올릴 수 있는
   표준 절차를 확보해, 계약상 요구되는 매뉴얼 제공 요건을 충족
2) 기존에 없던 애플리케이션 정상 종료 단계를 도입해, systemd 강제 중지로 인한 비정상 종료
   위험을 제거
3) 정지/기동 순서와 완료 판정 기준을 스크립트 로직에 내재화하여, 수동 절차에서 발생하던
   순서 누락·실수 가능성을 축소
4) 설계·구현 전 과정을 단독으로 수행
